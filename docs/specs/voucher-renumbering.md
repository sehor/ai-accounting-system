# 整理凭证号实施计划

状态：已实施。用户已批准本计划，并明确按日期整理也必须补齐全部缺号；整理不重建余额投影。

## 目标与默认规则

在“查凭证”页面增加“整理凭证号”，解决删除凭证造成断号、修改日期造成编号与日期顺序不一致的问题。参考用户提供的金蝶界面，沿用当前项目“记 + 数字”的统一字号规则。

- 每次选择一个账套中的一个会计期间，处理该期间全部未删除凭证，不受列表分页、关键字、日期筛选或勾选项影响。
- 包括手工凭证、单据生成凭证、固定资产凭证和月末结转凭证；包括已记账凭证。
- 仅允许 OPEN 期间；已结账期间需要先通过现有流程反结账。执行时再次检查期间状态。
- OWNER、EDITOR 可以预览和执行；VIEWER、REVIEWER、AGENT 不提供操作权限，后端独立校验。
- 凭证字固定为“记”，显示为只读项。
- 起始凭证号为正整数，默认 1；整个期间从此号码连续编号，不表示只整理原编号大于该值的凭证。界面明确说明这一点。
- 首版不做跨期间批量整理、定时整理或一键撤销；保留完整审计以便追溯。

## 整理规则

| 模式 | 排序及结果 |
| --- | --- |
| 按原凭证号补齐断号 | 按原编号的数值升序排列，依次从起始号编号。例如 1、3、6 → 1、2、3。 |
| 按凭证日期重新编号（默认） | 日期升序，同一天按原编号数值升序，再以创建时间、UUID 稳定排序，从起始号连续编号，同时补齐全部缺号。 |

数字排序不得使用字符串排序，避免 10 排在 2 前面。相同输入反复预览、执行，排序结果必须稳定。

只修改真正变化的凭证。空期间或编号已符合所选规则时返回正常无变更结果，不报错、不新增凭证修订。

参数验证覆盖起始号、最终号和事务内临时号的范围，保持与现有 bigint 取号逻辑兼容，并为后续取号留出空间。发现未完成历史规范化的异常字号时明确阻止整理，不静默跳过。

## 页面交互

1. 在 `VoucherListPage.tsx` 工具栏新增“整理凭证号”。权限不足时隐藏入口。
2. 打开独立 `VoucherRenumberModal`：会计期间、凭证字“记”、起始号、两种整理方式。列表仅筛选一个期间时沿用该期间；跨期间时要求明确选择单个期间。
3. 点击“预览整理”：显示期间、总凭证数、需修改数、新编号范围，以及日期、摘要、原字号、新字号的变更清单。长清单分页展示，但计算始终覆盖整个期间。
4. 没有变化时显示“当前期间无需整理凭证号”，允许关闭，不弹警告错误框。
5. 有变化时显示“确认整理”；执行中禁用重复点击。参数变化即作废旧预览。确认必须使用当前参数对应的预览。
6. 预览失效时提示“凭证已发生变化，请重新预览”，不能悄悄重新计算后直接执行。
7. 完成后显示“已整理 N 张凭证”，刷新凭证列表、已打开的凭证详情/标题和账簿查询缓存；避免遗留旧字号搜索导致误以为凭证丢失。

## 后端契约

沿用现有 Controller → Service → Repository 分层、Java record DTO、ApiProblemException 和 OpenAPI 生成流程，使用 api-and-interface-design 技能约束接口边界。不新增框架依赖。

建议接口路径：

- `POST /v1/ledgers/{ledgerId}/vouchers/renumber:preview`
  - 输入：`periodId`、`mode`（`NUMBER_ORDER` / `DATE_ORDER`）、`startNumber`（十进制字符串，默认 `"1"`）。
  - 返回：统计、旧号→新号清单、服务端生成的 `previewFingerprint`。首版完整计算返回，由前端分页展示；不套用现有凭证列表 500 条限制。
  - 指纹包含账套、期间、模式、起始号及该期间全量凭证的 ID、版本、日期、类型、编号；不能只覆盖发生改号的凭证。
- `POST /v1/ledgers/{ledgerId}/vouchers/renumber:execute`
  - 输入：相同参数及 `previewFingerprint`；请求头必须携带 `Idempotency-Key`。
  - 后端重新读取事实并独立计算编号，不接受客户端提供的改号映射。
  - 返回：操作 ID、变更数量、编号范围及是否无变化。
  - 同一幂等键、相同请求返回原结果；同一键不同请求返回冲突。成功后网络重试不得重复执行。

错误沿用项目 Problem Details：参数无效、权限不足、期间不存在/已关闭、预览过期（409）、幂等键冲突（409），提供稳定业务错误码和中文界面提示。

## 事务、并发与唯一约束

现状依据：

- `JdbcVoucherRepository.nextVoucherNumber` 使用“账套 + 期间 + 凭证字”的事务级 advisory lock。
- `BalanceProjectionService.requireOpenPeriod` 的实现会锁定会计期间行；创建凭证先取得期间锁，再取得取号锁。
- `uk_voucher_business_key` 是未删除凭证的 `(ledger_id, period_id, voucher_type, voucher_number)` 唯一索引。
- V60 的凭证更新触发器在编号变化时使明细账检查点失效。

执行流程：

1. 校验账套权限；先取得账套 KEY SHARE 锁，与后台余额重建的锁顺序协调；再通过整理专属 Repository 取得期间锁并确认 OPEN，然后取得同期间“记”的取号锁。整理服务不依赖余额投影服务。
2. 以固定顺序锁定目标凭证，读取全量事实并核验预览指纹。复核新增、更新、删除、自动凭证替换、版本恢复及结账入口都与期间锁协调；补齐存在的缺口，统一加锁顺序。
3. 计算最终映射，仅保留需要变化的行。
4. 在同一数据库事务内两阶段更新：先转入高于当前最大号及目标最大号的独立临时数字区间，再更新为最终连续数字。临时编号不对外提交，也不进入业务审计结果。
5. 每张变化凭证只增加一次业务版本/修订号，更新修改人和时间，记录最终旧号→新号审计，保存幂等执行结果，最后一起提交。出错全量回滚。

不删除重建凭证，不调用普通凭证修改接口逐张改号，不改变凭证 ID、日期、分录、金额、状态、来源关联或幂等创建键。纯改号不发布重新记账事件，不创建余额重建任务，不更新余额投影及其处理位置。原有明细账检查点仍按现有触发器失效以刷新字号；这不涉及科目/辅助核算余额投影重建。前端仅刷新凭证、审计、明细账及辅助明细账缓存，不刷新全部余额和报表查询。

计划新增整理操作记录表，用于执行幂等和操作追踪，保存操作 ID、账套/期间/操作者、幂等键、请求摘要、模式、起始号、统计及完成结果。唯一约束限定幂等键作用域。迁移序号实施时按仓库最新版本确定，不改已执行的迁移。

逐凭证复用 `audit_revision`，动作 `RENUMBER`，记录完整业务快照和统一操作 ID。旧快照保持历史真实性。检查版本恢复与整理后编号的相互影响：不得覆盖其他凭证的现有号码或恢复异常业务字符串；有冲突时明确提示。

## 验收与验证命令

必须覆盖：

- 删除后断号补齐；日期修改后重排；同日稳定排序；2 与 10 的数值排序；非 1 起始号。
- 空期间、无需整理、只有一张凭证；超过 500 张的期间完整处理；已删除凭证不参与；不影响其他期间/账套。
- 手工与自动凭证混排、已记账凭证改号；整理后自动凭证重算仍保留其新号；下一张新凭证取整理后的最大号 + 1。
- 编号交换不触发唯一约束冲突；中途失败回滚；审计不包含临时号；业务版本只递增一次。
- 预览后新增、删除、改日期、改号、结账；两人同时整理；执行请求重试；跨账套或无权限请求。
- 整理前后分录、金额、状态及来源关联一致；列表、详情、明细账、打印/导出的当前字号一致。
- 前端期间默认值、必选期间、模式切换、起始号验证、预览作废、无变化提示、提交中禁用、冲突后重新预览。

命令在项目根目录使用 PowerShell 执行：

```powershell
.\mvnw.cmd -q -DskipTests compile
pnpm --dir frontend exec vitest run src/pages/VoucherRenumberModal.test.tsx src/pages/VoucherPages.test.tsx
$env:OPENAPI_URL = 'http://127.0.0.1:8080/v1/openapi.json'
pnpm --dir frontend api:generate
graphify update .
```

优先使用已运行的 8080 后端做 HTTP 验证，在隔离的临时测试账套中运行并清理。需要测试数据库时使用 `./start-backend-test.ps1`（默认 18080），不用另起 JUnit Spring 上下文代替接口验证。纯排序算法可用不启动 Spring 的定向单元测试；事务失败注入或并发问题如无法通过 HTTP 充分验证，再运行单个必要 Java 测试类。

不运行仓库范围的前端 test/lint/typecheck/build；若定向验证无法覆盖，先报告具体缺口，再请求扩大验证范围。

代码风格沿用现有 `@Transactional` 服务方法、record 请求响应及 `problem(status, code, title, detail)`，不将排序、授权或事务逻辑放入 Controller/React 组件。首版保持同步事务执行，不引入后台任务系统。
